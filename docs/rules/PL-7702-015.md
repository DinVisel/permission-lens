# PL-7702-015 — Registry flags a storage/init risk

**Severity:** medium
**Confidence:** certain
**Needs chain data:** no (pure registry data)

## Condition

The registry entry matched by address has `properties.initialization:
"unprotected"` and/or `properties.storage: "plain"`.

## Why it matters (LEARNING.md §5.5)

- **Unprotected initialization:** a 7702 delegation can't run a
  constructor. If the delegate needs setup (e.g. "set my owner/guardian"),
  and that setup isn't itself protected by a signature check, an observer
  can front-run it — calling `initialize` before you do, from a
  transaction they control.
- **Non-namespaced ("plain") storage:** switching from one delegate to
  another reuses the same storage slots. A delegate that doesn't use
  namespaced storage (ERC-7201) may misread a previous delegate's leftover
  data, or have its own data misread by the next one.

This is exactly the class of bug documented in
[`IMPLEMENTATION_PLAN.md` §11](../../IMPLEMENTATION_PLAN.md#11-securing-the-project-itself)
("Lessons from SessionKit").

## What to do

If you're setting this delegate up for the first time, do it in the same
transaction (or immediately after) so nobody can front-run the
initialization. If you're switching from a different delegate, check
whether the new one's documentation addresses storage collisions.
